# MacNet Lab

**让 AI 看懂你的网络，再沿着证据找到问题。**

MacNet Lab 是一个面向 macOS 的拓扑感知网络运维工作台：用拖拽拓扑描述设备、接口和服务，结合当前接入位置、路径检测和故障证据，帮助 AI 缩小排查范围。既可运行在常开 Mac 上持续监控，也可装在 MacBook 上进行现场维护；单网、有线、Wi-Fi 或多接口接入均属于目标场景。

> **项目状态：规划阶段。** 当前仓库包含项目说明与开发路线，尚无可运行程序。下文描述的是目标设计，功能进度以路线图中的勾选状态为准。

## 为什么做这个项目

网络出问题时，“能不能 Ping 通”往往不够。

- MacBook 接在机房网线或某个 AP 下，当前能检查哪些设备，问题更可能出在哪一段？
- 同一个 Wi-Fi 名称下，MacBook 换到另一个 AP 后体验变差，接入信息和检测结果发生了什么变化？
- 只有一条连接时能否完成排障，同时连接有线与 Wi-Fi 时又该怎样分别观察？
- 普通网页能打开，但经过 Nikki 的请求失败，应该检查哪里？
- 手机找不到共享打印机，是网络发现、Mac 的打印服务，还是 USB 连接出了问题？
- Mac 上的 Minecraft 服务器连接不上或卡顿，是网络路径异常、服务未响应，还是主机资源不足？
- 故障恢复后，当时的日志和检测结果还能不能找到？

MacNet Lab 希望把这些线索放在一起：**拓扑说明环境，检测记录事实，黑匣子保留现场，AI 解释证据。**

## 两种使用方式，按当前连接工作

- **现场维护**：MacBook 接入获授权的有线网络或任意一个 AP，选择对应站点的拓扑，识别当前接口、地址、网关、DNS 和可读取的 Wi-Fi 信息，再从这个位置开展检测与排障。
- **常驻监控**：常开 Mac 持续检测、保存历史和故障证据；有多个可用接口时，分别记录各自的观测结果。

只有一张网卡或一条可用路径也能使用。多网卡并行检测是增强能力，不是安装、建图或排障的前提。MacBook 离开现场、休眠或退出程序后，本机停止采集；需要持续监控时，由仍在线的常驻主机承担。

## 场景一：单网络、单 AC 与多个 AP

下面以 AC 旁挂、AP 经交换机接入为示意，实际接线与转发方式由站点拓扑描述：

```text
上游网络 ── 路由器 / 网关 ── 交换机
                              ├── 有线 ── AC
                              ├── 有线 ── AP 1
                              ├── 有线 ── AP 2
                              ├── 有线 ── AP 3
                              └── 有线 ── MacBook（机房接入示例）

AC ── 管理关系 ── AP 1 / AP 2 / AP 3
AP 1 或 AP 2 或 AP 3 ── Wi-Fi ── MacBook（无线接入示例）
以上 MacBook 为同一台设备，不要求同时连接有线和 Wi-Fi。
```

AC、路由器和交换机可以是独立设备，也可以集成在一台设备中；AC 对 AP 的管理关系不直接等于用户流量的实际转发路径。MacBook 改变接入位置时，更新的是当前观测位置，不把整个站点拓扑重新定义成它当前可见的设备集合。

维护范围取决于管理地址是否可达、设备提供的管理能力和已有授权。例如访客 Wi-Fi 与管理网隔离时，应标明管理面不可达，提示使用获授权的管理接入，不自动更改 VLAN、路由或访问控制。

## 场景二：双路径、共享打印与 Minecraft

这是一个可选的家庭 / 实验室场景，不是软件运行的必要条件：

```text
光猫
├── 有线 ── 路由器 1
│            └── Wi-Fi ── Mac（无线接口）
└── 有线 ── 路由器 2（KWRT）
             ├── 运行：Nikki
             └── 有线 ── Mac（有线接口）

上面两处 Mac 是同一台设备：
Mac
├── 运行：监控与 AI 运维工具
├── 运行：打印共享服务与队列
├── 运行：Minecraft 服务器
└── USB ── 打印机
```

Mac 是同一台设备，网线连接路由器 2，同时通过 Wi-Fi 连接路由器 1；打印机通过 USB 接入 Mac，由 Mac 提供打印共享；Minecraft 服务器也运行在这台 Mac 上。两条网络路径共用光猫，不代表两条完全独立的互联网线路。

图中的“运行”表示服务归属，不是物理连线。Nikki 是路由器 2 上的服务，不是所有流量都必经的一台设备。手机所在网络、网段、DHCP/DNS 角色及实际出口，需要在配置时明确。

## 拓扑不是装饰，是 AI 的网络上下文

画布是结构化网络模型的编辑入口。AI 需要读取的不只是一张图片，还包括：

1. **设备与接口**：网关、交换机、AC、AP、服务器、终端和外设，以及各自接口的连接对象。
2. **物理连接与逻辑关系**：有线（Ethernet）、Wi-Fi、USB 连到具体接口；管理关系、服务归属和网络依赖单独表达。
3. **网络角色与服务**：网段 / VLAN、网关、DHCP、DNS、AC 管理的 AP，以及按需配置的 Nikki、打印、Minecraft 等服务。
4. **当前观测位置**：这台 Mac 使用哪个接口、连接哪个网络或 AP，以及当前可达的管理范围。
5. **检测路径与证据**：从哪个位置和接口发起检测、访问哪个目标、何时异常、有哪些日志。

用户声明的拓扑和实际检测到的状态分别保存。未知字段保留未知；发现两者不一致时提示差异，不自动改写网络关系。

## 计划提供的能力

### 拼积木描述网络

- 拖入网关、交换机、AC、AP、服务器、普通设备和外设，连接具体接口。
- 按站点保存拓扑与检测配置；进入现场后由用户选择对应站点，不凭相同 SSID 自动认定是同一网络或复用设备凭据。
- 为设备挂载服务和检测项目。
- 区分拓扑编辑与监控查看，支持保存和导入导出。
- 保存拓扑、测试连接、启用监控分别操作；不因拖入设备自动安装探针或写入 SSH 公钥。

### 识别接入位置，支持单接口和多接口检测

- 有线：连接状态、协商速率及可读取的链路指标。
- Wi-Fi：关联状态、SSID、BSSID、信号质量及可读取的连接速率；字段按目标 macOS 版本与权限适配，不可读取时标为未知。
- 针对当前可用的接口，检测网关、延迟、丢包、DNS、HTTPS，以及按需配置的服务；未连接的可选接口不作为故障告警。
- 自动识别网卡，不写死 `en0`、`en1`；验证 DNS 与后续请求的实际检测路径。
- 有多个接口时独立检测，不允许借另一条连接的成功结果将异常路径标为正常；路径无法确认时显示未知。
- 接入接口、地址、网关或 BSSID 改变时，记录接入变化和检测中断，按观测位置区分历史；用户主动切换与计划外断线分别记录。
- 按同一时间轴查看单路径历史或对比多条路径，标明 VPN、系统代理或隧道对检测的影响。

Wi-Fi 信号反映 Mac 所在位置及当前关联 AP 的情况；连接速率不等于实际下载速度，也不能代表其他房间或终端的体验。

### 在单 AC 多 AP 网络中定位问题

- 用可读取的 BSSID 结合用户维护或已授权导入的 AP 清单，关联当前接入 AP；同名 SSID 不作为同一 AP 的依据。
- AP 与 BSSID 的映射允许一对多，具体设备名称和部署位置来自拓扑或管理数据，不由一个 BSSID 猜出完整拓扑。
- 在 AP 间移动时保留信号、网关、DNS、目标服务的检测记录，帮助区分无线接入、AP 上联、地址分配和共同上游的问题。
- AC / AP 深度指标通过已授权且实际可用的设备接口按需适配；没有控制器接入时，仍能从 Mac 当前连接开展基础检测。
- 当前 AP 下的体验、其他 AP 的管理状态和其他终端的体验分别表达；一台 Mac 接入一个 AP，不意味着同时测到了所有 AP 的无线覆盖。

### 沿服务链排查共享打印

```text
手机 → 所在网络 → Mac 打印共享服务 → 打印队列 → USB → 打印机
```

分别观察服务可达性、共享与队列状态、USB 设备识别和打印机报告的状态。USB 打印机不强制配置 IP，不用 Ping 判断在线；日常监控不自动发送测试打印任务。

手机端的发现与打印协议兼容性需要实际验证，不把“开启 Mac 打印共享”直接视为所有手机都可使用。

### 区分 Minecraft 服务故障与网络故障

Minecraft 作为 Mac 上的一项服务建模，记录服务类型、监听地址、端口及相关接口。Java / Bedrock 版本、启动方式和玩家接入路径按实际配置填写，不预设端口或公网开放方式。

- 分别记录本机进程状态、服务协议响应和玩家接入路径，避免把“进程还在”直接当成“玩家可以正常连接”。
- 按服务端支持的只读状态协议，计划读取版本、在线人数和状态请求耗时；未提供的数据标为未知。
- 结合当前可用网络路径的检测记录，以及 Mac 和服务进程的 CPU、内存、磁盘剩余空间，分析连接失败或卡顿的可能原因。
- 异常时保存状态变化和已授权范围内的服务日志，与网络故障共用事件时间轴。
- 本机检测不代表其他终端或公网玩家的实际可达性；这些结论需要对应位置的探测证据。

日常监控只读取状态，不自动重启或关闭服务器，不修改服务配置、世界存档、插件或玩家权限。发给 AI 的证据不包含世界存档、完整聊天记录或玩家身份信息。

### 用黑匣子保留故障证据

- 故障前持续保留轻量指标与有大小限制的近期日志。
- 异常时补采已授权的只读快照，恢复后补采恢复信息。
- SSH 失败时保留已有证据，并记录采集失败的原因。
- 合并重复告警，记录故障开始、恢复和证据时间，设置数据保留与容量限制。
- 区分正常、异常、未知、暂停、观测位置变化和监控中断；Mac 休眠、离场或采集程序退出不记作全网断网，也不将中断期间标为正常。

### 让 AI 根据证据排障

选择一个事件，询问“这个 AP 下为什么上不了网”“刚才为什么断网”“为什么手机打印不了”或“Minecraft 为什么连不上”。AI 结合站点拓扑、当时的观测位置和所选证据给出：

- 观察到的事实与对应记录。
- 可能原因、疑似故障范围及判断依据。
- 还缺少什么证据，以及下一步的只读检查建议。

AI 首先只负责分析和受限的只读采集。AI 服务不可用时，本地监控、记录与回放继续工作。后续如接入多个提供商，日志外发目的地应明确展示，不静默切换。

## 拟采用的技术方案

| 模块 | 方案 | 用途 |
| --- | --- | --- |
| 界面 | Vue 3 + TypeScript + Vue Flow | 编辑拓扑、查看路径和事件 |
| 本地 API | Python + FastAPI | 配置、历史查询和实时状态推送 |
| 检测与监控 | 独立的异步采集进程 | 当前接入识别、单 / 多路径检测、事件判断与调度 |
| 站点模型 | 结构化拓扑、接口与观测上下文 | 区分物理连接、AC 管理关系、服务依赖和检测位置 |
| 远程只读采集 | AsyncSSH | 获取已授权设备的诊断信息 |
| 本地存储 | SQLite | 配置、检测结果、事件与受限快照 |
| macOS 适配 | 本机网络、Wi-Fi、USB、打印与资源状态接口 | 获取宿主机、进程和外设状态 |
| Minecraft 适配 | 按实际服务端选择的只读状态协议与日志采集 | 获取服务响应、版本、人数及故障证据 |
| AI 集成 | 独立适配层，优先评估 Codex App Server | 事件问答、只读工具与审批交互 |

部署目标是 macOS，包括用于现场维护的 MacBook 和用于常驻监控的 Mac，界面通过浏览器访问。具体最低 macOS 版本、Intel / Apple Silicon 支持、安装与常驻方式，待目标机器验证后确定。当前尚无安装或启动命令。打印与 Minecraft 等服务按需启用，不要求安装本工具的每台 Mac 都运行这些服务。

## 安全与隐私设计

- 本地优先；不默认向公网开放管理接口。开放局域网访问时需配套认证与传输保护。
- 密码、SSH 私钥和 API 密钥不写入拓扑导出、日志或 Git 仓库；具体凭据存储方案随 macOS 适配确定。
- SSH 校验主机身份；远程采集限定命令、参数、执行时长与输出大小。
- 日志和设备输出作为不可信数据处理，不允许其中的文字改变 AI 权限或触发执行。
- 发给 AI 的资料限定在选定事件与必要上下文，并先移除凭据和敏感配置。
- 每次修改都需要明确授权，同一设备不并发执行多个变更。
- 恢复机制按具体动作设计并演练，不承诺统一的“45 秒必恢复”。
